# Экспорт и сбор метрик приложения учёта оборудования

В minikube я развернул VictoriaMetrics Single и настроил сбор метрик приложения и PostgreSQL. Для приложения подключил готовую библиотеку HTTP-метрик и добавил четыре бизнес-счётчика.

## Стек и экспортеры

Приложение состоит из API на Python 3.14 и FastAPI, интерфейса на Vue 3 с Nginx и PostgreSQL 18. Оно работает в namespace `default` профиля minikube `sre`. У API две реплики.

| Компонент                            | Версия и назначение                                         |
| ------------------------------------ | ----------------------------------------------------------- |
| VictoriaMetrics Single               | `v1.154.0`, хранение и сбор метрик в namespace `monitoring` |
| Helm chart `victoria-metrics-single` | `0.49.0`, release `vm-single`                               |
| `prometheus-fastapi-instrumentator`  | `8.1.0`, автоматические HTTP-метрики FastAPI                |
| `prometheus-client`                  | `0.26.0`, собственные бизнес-счётчики                       |
| Postgres exporter                    | `v0.20.1`, экспорт статистики PostgreSQL                    |

VictoriaMetrics использует PVC размером 1 GiB и хранит метрики семь дней. Её настройки находятся в [victoria-metrics-values.yml](../k8s/monitoring/victoria-metrics-values.yml). Установка выполнена через Helm по инструкции из задания:

```bash
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm repo update
helm install vm-single vm/victoria-metrics-single \
  --version 0.49.0 \
  --namespace monitoring \
  --create-namespace \
  --values k8s/monitoring/victoria-metrics-values.yml
```

## Как собираются метрики

Используется Pull-модель. Встроенный сборщик VictoriaMetrics Single опрашивает HTTP-адреса с метриками и сохраняет значения вместе со временем.

Сборщик находит Pod через Kubernetes service discovery. Аннотации `prometheus.io/scrape`, `prometheus.io/port` и `prometheus.io/path` находятся в `spec.template.metadata.annotations` Deployment. Так их получают сами Pod. Во время настройки я сначала добавил аннотации API в metadata Deployment, из-за чего сборщик не обнаруживал его Pod. После переноса аннотаций появились обе реплики.

API публикует метрики на порту `8000`, путь `/metrics`. Запросы к самому `/metrics` исключены из HTTP-статистики. В ней доступны число запросов и длительность обработки, в том числе `http_request_duration_seconds_count`, `_sum` и `_bucket`.

Метрики доступны внутри кластера без авторизации. Для проверки с компьютера используется `kubectl port-forward`; Nginx интерфейса не проксирует `/metrics` в API.

## Бизнес-метрики

| Метрика                       | Что считает                                |
| ----------------------------- | ------------------------------------------ |
| `equipment_created_total`     | Успешные создания экземпляров оборудования |
| `employees_created_total`     | Успешные создания сотрудников              |
| `equipment_assignments_total` | Успешные выдачи оборудования               |
| `equipment_returns_total`     | Фактически выполненные возвраты            |

Все четыре метрики имеют тип Counter. Они объявлены в [metrics.py](../backend/app/metrics.py) и увеличиваются в [services.py](../backend/app/services.py) после успешной фиксации транзакции. Повторный возврат не увеличивает счётчик, поскольку запись уже содержит время возврата.

Каждая реплика API ведёт собственные счётчики. Для общего значения я суммирую показатели реплик в запросе. При перезапуске процесса его счётчики обнуляются; они не заменяют историю операций в PostgreSQL.

## Метрики PostgreSQL

В [db-deployment.yml](../k8s/db-deployment.yml) я добавил контейнер `quay.io/prometheuscommunity/postgres-exporter:v0.20.1` в Pod PostgreSQL. Он подключается к `localhost:5432/equipment` и отдаёт метрики на `9187/metrics`. Пароль получает из существующего Secret `db-secret`.

Аннотации Pod указывают сборщику порт `9187`. Метрика `pg_up` показывает успешность подключения exporter к базе, а `pg_database_size_bytes` содержит размер базы в байтах.
