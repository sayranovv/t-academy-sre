# Контекст и инструкции проекта

## Назначение и стадия

Учебный проект курса SRE Т-Академии. Пользователь выбрал тему **учёт оборудования**.
Пользователь должен понимать всё приложение; простота важнее числа функций.
Обязательны frontend, backend, PostgreSQL, CRUD и 12 Factor; взаимодействие —
HTTP/REST с поддержкой HTTP/1.1. Стек должен подходить для небольшого учебного окружения.

На 2026-09-28 создана спецификация v1, реализации нет. Пользователь попросил сначала
аналитику, затем план разработки, затем код. Не считать описанные функции реализованными.
Не начинать кодинг автоматически при чтении этого файла.

Пользователь утвердил [план реализации](docs/implementation-plan.md) и поручил его
выполнение. Работать по этапам с разбором. Всё окружение с начала в Compose.
Первый этап — три варианта Product Design и выбор пользователя до реализации UI.
Стек утверждён: Python 3.14, синхронные FastAPI/SQLAlchemy 2/Psycopg 3, Pydantic 2,
Alembic, uv; Vue 3/TypeScript/Vite/Vue Router, npm/Node.js 24; PostgreSQL 18.
План уточняет предварительный выбор ниже; точные зависимости фиксировать lock-файлами.

Дизайн выбран: третий показанный вариант; уточнён палитрой пользователя.
UI-кит: PrimeVue 4, styled mode, Aura (@primeuix/themes), PrimeIcons.
Обязательный источник: [дизайн-система](docs/design-system.md) и её сохранённый макет.
Светлая тема; #f8f8f8 фон, #337418 primary, #5dd62c акценты, #202020 текст,
#0f0f0f заголовки. Ярко-зелёный не использовать для текста на светлом фоне.
Использовать готовые компоненты UI-кита, собственные компоненты только для
предметных композиций. Не добавлять второй UI-кит или Tailwind без задачи.

## Зафиксированный core

- Одна организация, один тип оператора — ответственный за оборудование. Сотрудник —
  получатель оборудования, не пользователь с учётной записью.
- Учёт физических экземпляров по уникальному инвентарному номеру, не складских количеств.
- Пять сущностей: `categories`, `equipment_models`, `employees`, `equipment`, `assignments`.
- Связи: категория 1:N модели; модель 1:N экземпляры; экземпляр 1:N выдачи;
  сотрудник 1:N выдачи. Сотрудники и экземпляры связаны M:N во времени через выдачи.
- Категория и производитель относятся к модели, не дублируются в экземпляре.
- Текущий получатель определяется выдачей с `returned_at IS NULL`.
  Не хранить `current_employee_id`, `is_assigned` или статус `issued` в оборудовании.
- Состояние экземпляра: `usable`, `unavailable`, `retired`. Доступность вычисляется
  по состоянию и отсутствию открытой выдачи. Выдавать можно только `usable` активному сотруднику.
- Одна открытая выдача на экземпляр: частичный уникальный индекс плюс транзакции
  с блокировкой строки оборудования. Все изменения соблюдают единый протокол блокировок.
- Выдача и возврат получают серверное время после блокировок. Задние даты и изменение
  получателя/экземпляра выдачи запрещены. Повторный возврат не меняет первое время.
- Историю выдач не удалять. Для справочников, сотрудников и оборудования есть полный CRUD;
  удаление связанных записей возвращает конфликт. Не использовать каскадное удаление истории.
- Деактивация сотрудника (`is_active=false`) и списание (`retired`) запрещены при открытых
  выдачах. Списанный экземпляр нельзя вернуть в оборот в MVP.
- Без авторизации, файлов, закупок, бухгалтерии, нескольких организаций, уведомлений,
  очередей и микросервисов в MVP. Учебный запуск — в закрытом окружении с синтетическими
  данными. Для публичного доступа отдельно спроектировать аутентификацию.

## Направление реализации

Предварительный выбор: Python + FastAPI, SQLAlchemy + Alembic; Vue 3 + TypeScript + Vite;
PostgreSQL. Это рекомендация для следующего этапа; версии и зависимости ещё не зафиксированы.
Один backend, один frontend; браузер использует относительный `/api/v1`.
Nuxt/SSR для внутреннего CRUD не являются требованиями; не добавлять без конкретной задачи.
После начала реализации миграции — источник истины о схеме; сейчас это database.md.

## Правила разработки

- Объяснения и документация — на русском; идентификаторы кода и БД — на английском.
- Не добавлять Redis, брокер, Kubernetes или новые предметные сущности без задачи.
- Конфигурация через окружение, секреты вне Git, зависимости фиксируются lock-файлами.
- Состояние приложения — в PostgreSQL, не в памяти backend или локальных файлах.
- Ограничения и конкурентные сценарии проверять на PostgreSQL, не SQLite.
- Проверять CRUD, FK/уникальность, двойную выдачу, выдачу против деактивации/списания,
  повторный возврат, откат транзакции, сохранение истории и ошибки сети в UI.
- Не объявлять 12 Factor, тесты или производительность подтверждёнными до проверки.

## Актуальная документация: Context7

Использовать `ctx7` CLI для вопросов о библиотеках, фреймворках, SDK, API, CLI и облачных
сервисах: синтаксисе, настройке, миграции версий, установке и специфичной отладке,
даже если ответ кажется известным. Не требуется для общего программирования,
предметной области, рефакторинга, скриптов с нуля, ревью и отладки бизнес-логики.

1. Сначала `npx ctx7@latest library <name> "<конкретный вопрос>"`.
   Использовать официальное написание; выбрать совпадение по релевантности, репутации,
   числу примеров и benchmark. При плохом совпадении уточнить название или запрос.
2. Затем `npx ctx7@latest docs <libraryId> "<одна тема или взаимодействие тем>"`.
   Пропустить `library` можно только если пользователь дал ID `/org/project`.
   Для версии использовать ID версии из результата `library`.
3. Не более трёх команд на вопрос. Отвечать по полученной документации.
   Не передавать секреты. Предпочитать Context7 веб-поиску документации библиотек.

Запускать запросы Context7 вне стандартной песочницы через предусмотренный механизм
разрешений. При DNS/network-ошибке повторить вне песочницы.
При quota error сообщить пользователю и предложить `npx ctx7@latest login` либо
`CONTEXT7_API_KEY`; не заменять документацию молча знаниями модели.
