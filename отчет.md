# Отчёт по проекту «Учёт оборудования»

## 1. Доменная область приложения

Приложение предназначено для внутреннего учёта оборудования одной организации.
Оно помогает ответственному сотруднику видеть, какие физические устройства находятся
в фонде, какое оборудование доступно для выдачи, кому выдан конкретный экземпляр и
какова история его использования.

Основной пользователь системы — оператор, отвечающий за оборудование. Сотрудники,
которым выдаются устройства, являются объектами учёта и не имеют собственных учётных
записей в приложении.

Приложение поддерживает следующие процессы:

1. Ведение справочника категорий и моделей оборудования.
2. Регистрацию физических экземпляров с уникальными инвентарными номерами.
3. Ведение списка активных и неактивных сотрудников.
4. Выдачу доступного оборудования активному сотруднику.
5. Возврат оборудования и его последующую повторную выдачу.
6. Просмотр текущего получателя и истории выдач.
7. Временное исключение оборудования из оборота и окончательное списание.
8. Поиск, фильтрацию и постраничный просмотр данных.

Система учитывает каждый физический экземпляр отдельно. Например, десять одинаковых
ноутбуков представлены одной моделью и десятью экземплярами с разными инвентарными
номерами. Доступность не хранится отдельным полем: устройство доступно, когда его
состояние равно `usable` и у него нет открытой выдачи.

В границы проекта не входят закупки, стоимость и амортизация, поставщики, полноценный
процесс ремонта, подразделения, местоположения, файлы, уведомления и авторизация.
Приложение рассчитано на закрытое учебное окружение.

## 2. Стек реализации

### Backend

- Python 3.14;
- FastAPI — HTTP/REST API и OpenAPI-схема;
- Pydantic 2 — проверка входных и выходных данных;
- SQLAlchemy 2 — ORM и управление сессиями;
- Psycopg 3 — драйвер PostgreSQL;
- Alembic — миграции схемы БД;
- Uvicorn — ASGI-сервер;
- uv — управление Python-зависимостями;
- pytest — интеграционные и конкурентные тесты.

Backend реализован как модульный монолит. HTTP-обработчики отделены от схем данных,
ORM-моделей и бизнес-операций. Обработчики CRUD синхронные; каждый запрос получает
отдельную сессию SQLAlchemy. Бизнес-операции выполняются в явных транзакциях, и
фиксация изменений завершается до отправки успешного HTTP-ответа.

### Frontend

- Vue 3;
- TypeScript;
- Vite;
- Vue Router;
- PrimeVue 4, тема Aura и PrimeIcons;
- стандартный `fetch` для HTTP-запросов;
- Vitest для модульных тестов;
- Playwright для браузерных сценариев.

Frontend является одностраничным приложением. Он использует относительный путь
`/api/v1`, поэтому не содержит адрес или учётные данные PostgreSQL. TypeScript-типы
контрактов генерируются из OpenAPI backend и не дублируются вручную.

### Хранение данных и окружение

- PostgreSQL 18.3 во всех окружениях;
- Docker и Docker Compose для development, tests и production;
- Nginx для раздачи готовой frontend-сборки и проксирования API по HTTP/1.1;
- GitHub Actions для автоматических проверок и сборки;
- Makefile как единая точка запуска типовых команд.

Версии Python- и Node.js-зависимостей зафиксированы в `uv.lock` и
`package-lock.json`. Образы контейнеров используют конкретные версии.

## 3. Основные сущности доменной области

### 3.1. Категория (`categories`)

Категория объединяет близкие типы оборудования, например ноутбуки, мониторы или
периферию. Основные поля: идентификатор, название, описание и служебные даты.
Название уникально без учёта регистра и крайних пробелов.

Одна категория содержит много моделей. Категорию нельзя удалить, пока на неё
ссылается хотя бы одна модель.

### 3.2. Модель оборудования (`equipment_models`)

Модель описывает разновидность устройства, а не отдельный физический объект.
Она содержит категорию, производителя, название, описание и служебные даты.
Нормализованная пара «производитель + название» уникальна.

Одна модель относится к одной категории и может иметь много физических экземпляров.
Производитель и категория не копируются в каждый экземпляр, что устраняет избыточность.

### 3.3. Сотрудник (`employees`)

Сотрудник является получателем оборудования. Сущность содержит уникальный табельный
номер, ФИО, необязательный email, признак активности и служебные даты.

Активному сотруднику можно выдавать несколько устройств. Деактивация запрещена,
пока у него есть открытые выдачи. Неактивный сотрудник сохраняется в истории и может
быть снова активирован.

### 3.4. Экземпляр оборудования (`equipment`)

Экземпляр представляет конкретное физическое устройство. Он содержит уникальный
инвентарный номер, ссылку на модель, необязательный серийный номер, примечание и
эксплуатационное состояние:

- `usable` — устройство исправно и может быть выдано;
- `unavailable` — временно недоступно;
- `retired` — окончательно списано.

Факт выдачи и текущий сотрудник в этой таблице не хранятся. Они вычисляются по
открытой выдаче. Списанное устройство нельзя вернуть в оборот. Модель экземпляра
нельзя менять после первой выдачи.

### 3.5. Выдача (`assignments`)

Выдача связывает сотрудника и экземпляр оборудования на определённый период.
Она содержит ссылки на сотрудника и оборудование, серверное время выдачи,
необязательное время возврата и примечания к обеим операциям.

Если `returned_at IS NULL`, выдача считается открытой. Частичный уникальный индекс
разрешает только одну открытую выдачу для экземпляра. История выдач не удаляется,
а сотрудник, оборудование и время выдачи после создания не изменяются.

Связи между сущностями:

```text
Категория 1 ── N Модель 1 ── N Экземпляр 1 ── N Выдача N ── 1 Сотрудник
```

Сотрудники и экземпляры образуют связь «многие ко многим во времени» через выдачи.
Схема соответствует третьей нормальной форме: каждый факт хранится в одном месте,
производные значения не дублируются, а неключевые атрибуты зависят от ключа своей
таблицы.

## 4. Соответствие методологии 12 факторов

### I. Кодовая база — Codebase

Frontend, backend, миграции, контейнерная конфигурация, тесты и документация находятся
в одном Git-репозитории. Из одной кодовой базы собираются development- и
production-окружения. Версия приложения однозначно связана с Git-коммитом.

**Соответствие:** полное в пределах проекта.

### II. Зависимости — Dependencies

Все зависимости объявлены явно. Python-зависимости описаны в `pyproject.toml` и
зафиксированы в `uv.lock`; frontend-зависимости — в `package.json` и
`package-lock.json`. Приложение не рассчитывает на случайно установленные библиотеки
хоста: сборка выполняется внутри контейнеров через `uv sync --frozen` и `npm ci`.

**Соответствие:** полное.

### III. Конфигурация — Config

Параметры подключения к БД, размеры пула, тайм-ауты, уровень журналирования и порты
передаются через переменные окружения. В репозитории находятся только примеры
`.env.example` и `.env.production.example`; production-пароль должен быть задан
снаружи и не имеет рабочего значения по умолчанию.

**Соответствие:** полное. Секреты не зашиты в код и не должны фиксироваться в Git.

### IV. Подключаемые ресурсы — Backing services

PostgreSQL рассматривается как подключаемый ресурс. Backend получает его адрес и
учётные данные из окружения и обращается к нему через стандартное сетевое соединение.
Экземпляр БД можно заменить изменением конфигурации без изменения кода приложения.

**Соответствие:** полное.

### V. Сборка, релиз, выполнение — Build, release, run

Сборка создаёт неизменяемые runtime-образы backend и frontend. На этапе запуска к ним
добавляется конфигурация окружения. Миграции выполняются отдельным одноразовым
процессом до запуска API; каждая реплика backend не запускает миграции самостоятельно.

**Соответствие:** полное для учебного Compose-окружения. Отдельного промышленного
реестра релизов и системы продвижения между средами в границах проекта нет.

### VI. Процессы — Processes

Backend не хранит пользовательское состояние в памяти или локальных файлах.
Единственный источник прикладного состояния — PostgreSQL. Перезапуск backend не
приводит к потере данных, а несколько реплик используют общую БД.

**Соответствие:** полное.

### VII. Привязка портов — Port binding

Uvicorn самостоятельно предоставляет HTTP-сервис на порту 8000. Nginx предоставляет
готовое приложение на порту 8080 и проксирует API. В development Vite слушает порт
5173. Порты задаются конфигурацией Compose; наружу публикуется только frontend на
localhost.

**Соответствие:** полное.

### VIII. Параллелизм — Concurrency

Приложение масштабируется увеличением числа одинаковых процессов backend через
`docker compose ... --scale api=2`. Реплики не координируются через локальную память.
Целостность конкурентных выдач обеспечивает PostgreSQL: блокировки строк, единый
порядок блокировок и частичный уникальный индекс открытой выдачи.

Работа двух реплик с общей БД и конкурентные операции проверены отдельно.

**Соответствие:** полное.

### IX. Утилизируемость — Disposability

Контейнеры запускаются без ручной подготовки: Compose ждёт healthcheck PostgreSQL,
затем выполняет миграции и запускает API. При SIGTERM Uvicorn прекращает приём новых
запросов, завершает текущую работу в пределах настроенного тайм-аута и вызывает
закрытие пула соединений. Для приложения настроено 20 секунд на завершение запросов,
для контейнера — 30 секунд.

**Соответствие:** полное; штатное завершение проверено на production-образе.

### X. Сходство сред разработки и эксплуатации — Dev/prod parity

Development, tests и production используют PostgreSQL 18, одну модель данных и одни
миграции. SQLite и отдельные упрощённые реализации для тестов не применяются.
Backend собирается из одного Dockerfile, а frontend использует Vite в разработке и
собранную тем же Node.js-проектом статику в production.

**Соответствие:** полное в части версий, схемы и зависимостей. Способ раздачи frontend
закономерно различается: Vite используется для разработки, Nginx — для production.

### XI. Журналирование — Logs

API и Nginx пишут журналы в stdout/stderr и не управляют файлами журналов внутри
контейнеров. Запись API содержит request ID, HTTP-метод, шаблон маршрута, статус и
длительность. Тела запросов, персональные данные и секреты в access-журнал не входят.
Сбор и хранение журналов остаются ответственностью среды выполнения.

**Соответствие:** полное.

### XII. Административные процессы — Admin processes

Миграции и заполнение демонстрационными данными запускаются отдельными командами
`make migrate` и `make seed`, используя тот же код и те же зависимости, что и API.
В production Compose миграция оформлена как одноразовый сервис, от успешного завершения
которого зависит запуск backend.

**Соответствие:** полное.

## 5. Результаты проверки

Соответствие подтверждено следующими проверками:

- 17 backend-тестов на настоящей PostgreSQL, включая конкурентные операции;
- 4 модульных frontend-теста;
- 5 Playwright-сценариев CRUD, выдачи, возврата, истории и обработки ошибок;
- запуск двух реплик API с общей БД;
- сохранение данных после перезапуска backend;
- liveness `200` и readiness `503` при временно отключённой БД;
- корректное завершение процесса по SIGTERM;
- production-сборка frontend, прямое открытие вложенных SPA-маршрутов и HTTP/1.1;
- запуск backend и Nginx от непривилегированных пользователей.

Во время локального измерения без нагрузки каждая реплика API использовала около
75 MiB памяти, Nginx — около 7 MiB, PostgreSQL — около 33 MiB. Эти значения являются
наблюдением в конкретном окружении, а не заявленным SLO.

Таким образом, приложение выполняет исходные требования: имеет frontend и backend,
хранит данные в PostgreSQL, реализует CRUD и предметные операции, использует HTTP/REST
и соответствует методологии 12 факторов в границах учебного проекта.
