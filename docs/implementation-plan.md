## Результат и технические решения

Учебный MVP: пять сущностей PostgreSQL, CRUD справочников и карточек, выдача,
возврат, история, поиск и фильтры. Модель и бизнес-правила существующих docs сохраняются.

- Python 3.14, FastAPI, Pydantic 2, SQLAlchemy 2, Psycopg 3, Alembic, Uvicorn; uv.
- Синхронные def-обработчики, отдельная сессия на запрос, явные транзакции;
  COMMIT до отправки успешного ответа.
- Vue 3, TypeScript, Vite, Vue Router; npm, Node.js 24; fetch без глобального хранилища.
- PostgreSQL 18 во всех окружениях.
- Всё с первого этапа разработки в Docker Compose: БД, backend, frontend.
  Vite для разработки; Nginx для статики и reverse proxy готовой сборки.
- Точные версии зависимостей фиксировать lock-файлами, образы конкретными версиями,
  не использовать плавающий latest.
- Авторизация, закупки, ремонты, Kubernetes, очереди, метрики и трассировка вне MVP.

## Этап 1. Выбрать визуальный дизайн

Через Product Design подготовить ровно три визуальных варианта списка оборудования
и карточки с получателем, действиями и историей. Дождаться выбора пользователя.
Затем зафиксировать цвета, типографику, таблицы, формы, статусы и основные действия.
Предусмотреть загрузку, пустые состояния, ошибки и конфликт выдачи.
Язык русский, основная поверхность desktop.

Готовность: выбран один вариант, понятен состав экранов; frontend следует ему.

## Этап 2. Каркас и контейнерное окружение

Монорепозиторий backend/frontend/docs; Compose-сервисы БД, API и frontend,
одноразовый процесс миграций. Исходники и автоматическая перезагрузка внутри
контейнеров разработки. Относительный /api/v1 проксируется frontend в backend.
Добавить пример env, gitignore и зафиксированные зависимости.

Команды: make dev, make stop, make migrate, make seed, make test, make lint, make build.
make dev ждёт готовности БД, отдельно применяет миграции, запускает приложение.
Реплики API не запускают миграции самостоятельно. Остановка не удаляет данные;
публикуемые порты привязываются к localhost.

Предусловие: запустить Docker Engine; CLI/Compose установлены, движок при планировании
был недоступен. Готовность: запуск одной командой, frontend обращается к API.

## Этап 3. Схема и seed

Первая миграция пяти таблиц по database.md: FK, CHECK, нормализованная уникальность,
частичный уникальный индекс открытой выдачи, индексы связей и истории.
Повторяемый seed с синтетическими доступными, выданными, недоступными, списанными
устройствами, активными/неактивными сотрудниками, закрытыми выдачами.
Seed не очищает БД, не перезаписывает пользовательские записи; конфликт с изменёнными
демонстрационными записями сообщает явно.

Готовность: миграции на пустой БД, безопасный повтор, проверка ограничений PostgreSQL,
сохранность данных при перезапуске.

## Этап 4. CRUD API

Категории → модели → сотрудники → оборудование. Разделить обработчики, схемы
контрактов и бизнес-операции. Маршруты, фильтры, поиск, пагинация по architecture.md.
Единые ошибки и проверка изменяемых полей, ожидаемые конфликты БД → 409.
Данные модели, категории и текущей выдачи доступны в ответах без отдельных запросов
на каждую строку UI. OpenAPI backend служит источником генерируемых TypeScript-типов.
Добавить /health/live и /health/ready.

Готовность: интеграционные проверки CRUD четырёх ресурсов; допустимое физическое
удаление работает, связанные записи удалить нельзя.

## Этап 5. Выдача и возврат

Выдача и повторяемый возврат по ID выдачи. Порядок блокировок: сотрудник → экземпляр
→ выдача; проверки после блокировок внутри транзакции. Реализовать деактивацию,
недоступность, списание, запрет смены модели использованного экземпляра.
Сохранить неизменяемость истории и серверное время; получатель и доступность вычисляются.

Готовность: двойная выдача невозможна; гонки со списанием/деактивацией безопасны;
повтор старого возврата не закрывает новую выдачу.

## Этап 6. Интерфейс и API

Список/карточка оборудования, список/карточка сотрудников, справочники.
Формы CRUD, фильтры, поиск, пагинация; состояние списков в URL. Выдача, возврат,
история, активация, состояния оборудования. Выбор сотрудников/моделей с серверным
поиском и пагинацией. Сохранять ввод при ошибке и блокировать повторное нажатие.
После конфликта объяснить причину и обновить карточку; после неопределённого результата
перечитать данные без автоматического повтора POST. Проверить соответствие макету,
клавиатурную навигацию и подписи полей.

Готовность: пользовательские сценарии выполняются в браузере без ручных запросов.

## Этап 7. Воспроизводимый запуск

Runtime-образы backend и frontend/Nginx без dev-зависимостей. HTTP/1.1 proxy и прямое
открытие вложенных frontend-страниц. Структурированные логи, request ID, завершение
и конфигурация тайм-аутов. GitHub Actions: backend, интеграционные тесты PostgreSQL,
frontend types/build, браузерные тесты; без автодеплоя. Обновить инструкции запуска,
миграций, seed, диагностики и AGENTS.md.

Готовность: чистый checkout воспроизводимо запускается; AC-01–AC-12 подтверждены.

## Контракты и настройки

- /api/v1/categories, /equipment-models, /employees, /equipment: CRUD.
- /api/v1/assignments: чтение и POST выдачи.
- PUT /api/v1/assignments/{id}/return: возврат. Без обычных PATCH/DELETE выдач.
- Списки: items, total, limit, offset; ошибки: error и request_id.
- OpenAPI описывает вычисляемые поля и вложенные краткие сведения; frontend не
  дублирует типы вручную.

Стартовые env-настройки: один worker; pool=5, без overflow; ожидание пула 5 с,
подключения 3 с, блокировки 2 с, SQL-запроса 5 с; readiness с бюджетом 2 с;
graceful shutdown 20 с, остановка контейнера 30 с. Это не обещания SLO.

## Проверки и учебная приёмка

Backend: pytest и настоящий PostgreSQL — CRUD, нормализация, UNIQUE/FK, неизвестные
и неизменяемые поля; фильтры/поиск/пагинация/ошибки; удаление и переходы состояний;
повторный возврат, история, откат. Конкурентные проверки через независимые соединения
и управляемую синхронизацию, без случайных задержек.

Frontend: Vitest и Playwright — ошибки и сохранение ввода; создание справочников,
сотрудника и экземпляра; выдача → возврат → новая выдача → история; удаление и отказ
при зависимостях; сеть/конфликт без повтора выдачи; макет и клавиатура.

Окружение: сохранность после перезапуска, две реплики API с общей БД, отключение БД
(liveness успешна, readiness нет), SIGTERM, измерение базовых ресурсов без обещаний.

После каждого этапа: демонстрация, краткий разбор кода, воспроизводимый сценарий проверки.
