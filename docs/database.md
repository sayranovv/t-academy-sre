# Логическая модель PostgreSQL, v1

Это спецификация будущих миграций, не исполняемая схема. Физическая реализация и
проверка на PostgreSQL будут на этапе разработки. ER-диаграмма — в [diagrams.md](diagrams.md).

## Общие соглашения

- Первичные ключи: `bigint`, генерируемые БД. Их значение не несёт бизнес-смысла.
- Все поля обязательны, кроме явно помеченных NULL.
- Время — `timestamptz`; обмен API — ISO 8601 в UTC. PostgreSQL хранит момент времени,
  а не исходное название часового пояса пользователя.
- `created_at` и `updated_at` есть у четырёх CRUD-сущностей; backend обновляет
  `updated_at` при записи. У выдачи вместо них времена событий.
- Все внешние ключи используют `ON DELETE RESTRICT`; каскадное удаление запрещено.
- Обязательные строки непустые после trim; необязательные пустые строки превращаются в NULL.
- Инвентарные/табельные номера: 1–64 символа ASCII `A-Z`, `0-9`, `.`, `_`, `-`;
  trim и верхний регистр перед сохранением, формат также проверяет БД.
- Названия: 1–120 символов, ФИО/название модели до 200, серийный номер до 120,
  email до 254, примечания до 2000. Проверки длины — API и БД.
- Для названий категорий и пары производитель/модель регистр не создаёт разные
  записи: уникальность по `lower(trim(...))`. Внутренние пробелы не нормализуются.

## Словарь данных

### categories — категории

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| id | bigint | PK |
| name | varchar(120) | Название; уникальное без учёта регистра и крайних пробелов |
| description | text, NULL | Описание, до 2000 символов |
| created_at | timestamptz | Время создания |
| updated_at | timestamptz | Время последнего изменения |

### equipment_models — модели

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| id | bigint | PK |
| category_id | bigint | FK → categories.id |
| manufacturer | varchar(120) | Название производителя |
| name | varchar(200) | Название модели, включая вариант, если он значим |
| description | text, NULL | Описание, до 2000 символов |
| created_at | timestamptz | Время создания |
| updated_at | timestamptz | Время изменения |

Пара нормализованных `(manufacturer, name)` уникальна. В MVP такая пара определяет
одну модель и одну категорию. Если две модификации различаются, их имена должны
различаться. Изменение категории модели влияет на все экземпляры; UI объясняет это.

### employees — сотрудники

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| id | bigint | PK |
| personnel_number | varchar(64) | UNIQUE, табельный номер |
| full_name | varchar(200) | Отображаемое имя, не уникально |
| email | varchar(254), NULL | Контакт; проверяется как email в API, не уникален |
| is_active | boolean | По умолчанию true |
| created_at | timestamptz | Время создания |
| updated_at | timestamptz | Время изменения |

ФИО — единое отображаемое значение, а не набор для разбора; сортировка по фамилии
отдельно не требуется. Отдел, должность и учётная запись не входят в модель.

### equipment — физические экземпляры

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| id | bigint | PK |
| inventory_number | varchar(64) | UNIQUE, инвентарный номер |
| model_id | bigint | FK → equipment_models.id |
| serial_number | varchar(120), NULL | Серийный номер, без глобальной уникальности |
| operational_state | varchar(16) | CHECK: usable / unavailable / retired; default usable |
| notes | text, NULL | Примечание, до 2000 символов |
| created_at | timestamptz | Время создания |
| updated_at | timestamptz | Время изменения |

Не храним категорию, производителя, получателя или вычисленную доступность.
Не вводим общее поле status, смешивающее состояние и факт выдачи.

### assignments — выдачи

| Поле | Тип | Назначение и ограничения |
|---|---|---|
| id | bigint | PK |
| equipment_id | bigint | FK → equipment.id; неизменяемо |
| employee_id | bigint | FK → employees.id; неизменяемо |
| issued_at | timestamptz | Серверное время выдачи; неизменяемо |
| returned_at | timestamptz, NULL | NULL = открытая выдача; устанавливается однократно |
| issue_note | text, NULL | Примечание при выдаче; до 2000 символов; неизменяемо |
| return_note | text, NULL | Примечание при возврате; до 2000 символов; устанавливается с returned_at |

Ограничения строки: `returned_at IS NULL OR returned_at >= issued_at`;
если `returned_at IS NULL`, то `return_note IS NULL`.
Ключевой индекс — UNIQUE по `equipment_id` только для строк `WHERE returned_at IS NULL`.
Это запрет двойной открытой выдачи на уровне БД, а не только UI.
Сотрудник может иметь несколько открытых выдач: уникального индекса по employee_id нет.

## Кардинальности и производные значения

| Связь | Кардинальность |
|---|---|
| Категория → модели | 0..N; модель принадлежит ровно одной категории |
| Модель → экземпляры | 0..N; экземпляр имеет ровно одну модель |
| Экземпляр → выдачи | 0..N; выдача относится ровно к одному экземпляру |
| Сотрудник → выдачи | 0..N; выдача относится ровно к одному сотруднику |

`available = operational_state == usable AND NOT EXISTS(open assignment)`.
`current_employee` и время текущей выдачи получаем соединением с открытой выдачей.
Статус выдачи «открыта/закрыта» вычисляется по returned_at.
Эти поля можно включать в ответы API, но не хранить как независимые столбцы.

## Почему модель в 3НФ

1. **1НФ:** в ячейках одно значение; нет массива устройств у сотрудника, списка
   получателей у устройства или нескольких выдач в одной строке. Каждая строка имеет ключ.
2. **2НФ:** обычные PK одноатрибутные. В альтернативном составном ключе модели
   `(manufacturer, name)` категория и описание зависят от всей пары: одно имя без
   производителя и один производитель без имени модель не определяют.
3. **3НФ:** неключевые атрибуты описывают только сущность, заданную ключом; нет
   транзитивных зависимостей неключевых атрибутов внутри отношения.

| Отношение | Основные функциональные зависимости |
|---|---|
| categories | id → name, description, timestamps; нормализованное name → id |
| equipment_models | id → category_id, manufacturer, name, description, timestamps; нормализованная пара manufacturer/name → id |
| employees | id → personnel_number, full_name, email, is_active, timestamps; personnel_number → id |
| equipment | id → inventory_number, model_id, serial_number, operational_state, notes, timestamps; inventory_number → id |
| assignments | id → equipment_id, employee_id, issued_at, returned_at, issue_note, return_note |

Например, цепочка экземпляр → модель → категория проходит через разные таблицы.
Если хранить category_id и manufacturer ещё и в equipment, возникнут дублирование
и риск обновить только часть экземпляров. Имя сотрудника также не копируется в выдачу.

Повторение текста производителя в разных моделях само по себе не нарушает 3НФ:
атрибутов, функционально зависимых от производителя (адрес, сайт и т. п.), здесь нет.
При их появлении потребуется отдельная сущность производителей.
`equipment_id` не определяет `employee_id` во всей истории — выдач может быть много.
Условная уникальность открытой выдачи не делает equipment_id ключом всей таблицы.

Нормализация не решает временные и межтабличные правила: их обеспечивают ограничения
и транзакции ниже. Схема не хранит снимки ФИО/названий на дату выдачи.

## Индексы

Помимо PK и описанных уникальных индексов:

- equipment_models(category_id), equipment(model_id) — связи и фильтры;
- assignments(equipment_id, issued_at DESC, id DESC) — история экземпляра;
- assignments(employee_id, issued_at DESC, id DESC) — история сотрудника;
- assignments(employee_id) WHERE returned_at IS NULL — открытые выдачи сотрудника.

Не добавлять индексы на каждый столбец. Подстрочный поиск сначала простой;
специализированные поисковые индексы — после измерений. FK на стороне ссылок
требуют осознанного индексирования, PK уже покрывают поиск родительской строки.

## Конкурентность и границы гарантий

Базовый уровень изоляции — READ COMMITTED. Backend единственный штатный писатель.
Все проверки состояния выполняются **после** получения блокировок, в той же транзакции,
что и запись. При исключении транзакция откатывается целиком.

Порядок блокировок для операций с выдачами: **сотрудник → экземпляр → выдача**.
При нескольких строках одного типа — по возрастанию id. Предварительное чтение
неизменяемых FK выдачи нужно только чтобы узнать, какие строки блокировать;
состояние после блокировок перечитывается.

| Операция | Протокол |
|---|---|
| Выдать | Заблокировать сотрудника FOR UPDATE, затем экземпляр FOR UPDATE; повторно проверить активность, usable и отсутствие открытой выдачи; проверить существование; создать выдачу; COMMIT |
| Вернуть | Прочитать FK по id выдачи; заблокировать сотрудника, экземпляр, выдачу; если уже закрыта — вернуть существующий результат; иначе установить время/примечание; COMMIT |
| Деактивировать | Заблокировать сотрудника; проверить отсутствие открытых выдач; изменить флаг; COMMIT. Строки оборудования не блокировать |
| Изменить состояние/модель экземпляра | Заблокировать экземпляр; проверить переход и наличие выдач согласно BR-09/BR-15; изменить; COMMIT. Сотрудников не блокировать |
| DELETE | FK RESTRICT защищают связи, включая конкурентное создание ссылок; ожидаемый конфликт преобразовать в HTTP 409 |

Выдача и деактивация сериализуются на сотруднике; выдача и списание — на экземпляре.
Смена состояния, начавшаяся первой, завершится до проверки новой выдачи. Обратный
порядок приведёт к обнаружению открытой выдачи и отказу в смене состояния.
Любые новые способы изменения данных должны соблюдать этот протокол.

Время события брать из часов БД **после** блокировок (например, clock_timestamp),
а не из времени начала долго ожидавшей транзакции. Чтобы не нарушить порядок при
коррекции системных часов назад, issued_at новой выдачи не раньше максимального
returned_at предыдущих выдач экземпляра; returned_at не раньше issued_at.
Это правило backend, не гарантия абсолютной точности физических часов.
Интервалы трактуются как [issued_at, returned_at): возврат и следующая выдача могут
иметь одинаковый момент. Запрет задних дат и исправления событий сохраняет порядок.

CHECK не должен читать другие таблицы. БД гарантирует FK, строковые CHECK и одну
открытую выдачу; активность сотрудника, допустимость переходов, неизменяемость истории
и отсутствие пересечения закрытых интервалов гарантирует протокол backend.
Прямые административные SQL-изменения могут нарушить эти правила; если появится второй
писатель/импорт задних дат, понадобятся дополнительные ограничения/триггеры и новая спецификация.
Это осознанная граница MVP, а не утверждение о полной защите произвольных SQL-записей.

Примечания закрытой выдачи менять нельзя. История сохраняется через отсутствие
DELETE/обычного PATCH выдач в API и FK RESTRICT; миграции и seed запускаются отдельно.
