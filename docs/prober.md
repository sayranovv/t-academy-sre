# Пробер доступности

`backend/app/prober.py` — отдельный процесс без импорта FastAPI-приложения,
доступа к БД и зависимости от его конфигурации. Он использует существующий образ API,
но запускается командой `python -m app.prober` в отдельном Pod с одной репликой.

## Проверка

В Kubernetes цель — `http://web:8080/health/ready` в namespace `default`.
Проверяется путь через Nginx, API и подключение API к PostgreSQL. Это внутренняя
проверка: внешний доступ к кластеру, браузер и корректность выдачи она не проверяет.
Каждый запрос попадает в одну из реплик API, а не проверяет их все одновременно.

Успех — HTTP 200 и JSON с `status=ready`, `database=connected`.
Ошибка соединения, HTTP-ошибка, перенаправление, неверный JSON или тайм-аут
считаются неуспехом. Тело ответа ограничено 16 KiB. Повторных попыток внутри одной
проверки нет. После неуспеха процесс продолжает работу.

| Переменная | Значение по умолчанию |
|---|---|
| `PROBE_TARGET_URL` | Обязательный HTTP(S)-адрес без учётных данных |
| `PROBE_INTERVAL_SECONDS` | 30 секунд между началами проверок |
| `PROBE_TIMEOUT_SECONDS` | 5 секунд сетевого ожидания |
| `PROBE_METRICS_PORT` | 9101 |

Проверки не перекрываются; если проверка заняла весь интервал, следующая начинается
после её завершения. Тайм-аут стандартного HTTP-клиента ограничивает сетевые ожидания,
а не является строгим общим дедлайном, включая DNS. Ответ, полученный позже заданного
времени, также считается неуспешным. SIGTERM/SIGINT останавливают цикл после текущей
проверки и закрывают HTTP-сервер метрик.

## Метрики

На `/metrics` пробера доступны:

- `probe_checks_total{result="success"}`;
- `probe_checks_total{result="failure"}`.

Обе серии существуют с нулевыми значениями ещё до первой проверки.
После перезапуска процесса счётчики обнуляются; для SLI используются приросты
за окно с обработкой сбросов, а не накопленные значения напрямую.

SLI = прирост успехов / (прирост успехов + прирост неуспехов) × 100%.
При отсутствии проверок показатель не определён. Недоступность самого пробера
нужно отслеживать отдельно по `up` его scrape-target: пропажа наблюдений не означает
успех приложения. Этот SLI основан на результатах периодических проверок;
для TBSLO нужно дополнительно определить правило агрегации результатов по минутам.

## Запуск

Локально из каталога `backend` в окружении с установленными зависимостями проекта:

```bash
PROBE_TARGET_URL=http://localhost:8080/health/ready .venv/bin/python -m app.prober
```

Метрики: `http://localhost:9101/metrics`. Сам backend и Nginx запускаются отдельно.

Для minikube подготовлен `k8s/monitoring/prober.yml`. В образе
`t-academy-equipment-api:0.1.5` должен присутствовать новый модуль:

```bash
minikube -p sre image build -t t-academy-equipment-api:0.1.5 backend
kubectl --context sre -n default apply -f k8s/monitoring/prober.yml
kubectl --context sre -n default rollout status deployment/equipment-prober
kubectl --context sre -n default logs deployment/equipment-prober
kubectl --context sre -n default port-forward svc/equipment-prober 9101:9101
```

Deployment содержит аннотации сбора метрик по тому же образцу, что существующий
Deployment API. При действующем обнаружении Pod в VictoriaMetrics отдельный
scrape-job не нужен. После запуска необходимо проверить появление пробера на
`/targets` VictoriaMetrics и рост его счётчиков в vmui.
Readiness самого Pod проверяет экспорт метрик и не зависит от готовности цели:
авария приложения не должна выводить наблюдатель из готовности.

Манифест и команды подготовлены; сами по себе они не подтверждают развёртывание
или сбор метрик в кластере. Образ работающих реплик API также нужно обновить,
чтобы начали экспортироваться добавленные счётчики технических ошибок операций.
