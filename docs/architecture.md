# Архитектурные решения v1

## Направление стека

Реализованная основа: Python + FastAPI для одного backend,
SQLAlchemy и Alembic для доступа к БД и миграций; Vue 3 + TypeScript + Vite для SPA;
PostgreSQL. План реализации уточнил стек: Python 3.14, синхронные SQLAlchemy 2 и
Psycopg 3, Pydantic 2, uv; Node.js 24 и PostgreSQL 18. UI: PrimeVue 4 с Aura,
PrimeIcons и пользовательским preset по design-system.md. Точные зависимости
фиксируются lock-файлами. Это реализованный стек проекта.

Python соответствует первоначальному намерению пользователя. Vue SPA достаточно
для закрытого CRUD-интерфейса: SEO и серверная генерация страниц не требуются.
Поэтому Nuxt и отдельный сервер рендеринга не входят в основу. Node.js предполагается
как инструмент сборки frontend, не как второй backend. NestJS не исключён из-за
недоказанного расхода памяти — он просто не нужен для выбранного направления.
Ресурсоёмкость проверим измерением, а не обещаниями о фреймворках.

Backend — монолит с модулями справочников, оборудования, сотрудников и выдач.
HTTP-обработчики валидируют контракт; бизнес-операции управляют транзакциями;
слой БД хранит данные и ограничения. Не создавать универсальный repository framework,
CQRS, event bus или микросервисы ради пяти таблиц.

## Контракт HTTP/REST

Префикс `/api/v1`, JSON, совместимость с HTTP/1.1. Через общий origin браузер получает
статику и API; frontend использует относительный путь. API не зависит от cookie-сессий
или локального состояния процесса. Авторизации в закрытом учебном MVP нет.

| Ресурс | Операции |
|---|---|
| /categories | GET список, POST создание |
| /categories/{id} | GET, PATCH разрешённых полей, DELETE без моделей |
| /equipment-models | GET список, POST создание |
| /equipment-models/{id} | GET, PATCH, DELETE без экземпляров |
| /employees | GET список, POST создание |
| /employees/{id} | GET, PATCH включая is_active, DELETE без выдач |
| /equipment | GET список, POST создание |
| /equipment/{id} | GET, PATCH включая operational_state, DELETE без выдач |
| /assignments | GET история/открытые выдачи, POST выдача |
| /assignments/{id} | GET выдача |
| /assignments/{id}/return | PUT возврат; повтор возвращает первый сохранённый результат |

POST выдачи принимает equipment_id, employee_id и необязательный issue_note.
PUT возврата принимает только необязательный return_note. ID и времена генерирует сервер.
Повтор PUT с другим примечанием не переписывает уже закрытую выдачу.
Для исправления истории отдельного endpoint нет. CRUD-требование курса покрывается
четырьмя другими ресурсами, а выдачи имеют предметный жизненный цикл.

PATCH допускает только описанные изменяемые поля; неизвестные и read-only поля
отклоняются с 422. Для обычных описательных правок MVP использует last-write-wins;
защита от потерянных изменений через версии/ETag — отдельное расширение.
Проверки выдачи и состояний не используют last-write-wins, а выполняются под блокировками.

| Ответ | Значение |
|---|---|
| 200 | Успешное чтение/изменение/возврат |
| 201 | Создание, включая выдачу; возвращается созданный объект |
| 204 | Удаление без тела |
| 404 | Запрошенный объект или переданный ID связанного объекта не найден |
| 409 | Дубликат, зависимые записи при удалении, недопустимое состояние или конкурентная выдача |
| 422 | Некорректные поля, формат, неизвестные или read-only поля |
| 503 | Недоступна обязательная зависимость или превышено ожидание ресурса |
| 500 | Неожиданная ошибка; детали только в серверном журнале |

Ошибки имеют единый объект: `error.code` (стабильный машинный код), `error.message`
(безопасный текст), `error.details` (необязательные поля формы), `request_id`.
Примеры кодов: equipment_already_assigned, employee_inactive, resource_in_use,
invalid_state_transition, duplicate_inventory_number.
Сбой COMMIT/обрыв ответа может иметь неопределённый для клиента результат:
UI перечитывает данные, не считает каждый 5xx доказательством отката.

Списки возвращают `items`, `total`, `limit`, `offset`. По умолчанию limit=20,
максимум 100, offset ≥ 0. Порядок по умолчанию id ASC; история issued_at DESC, id DESC.
Сортировки разрешены только из фиксированного набора, с id как дополнительным ключом.
Offset-пагинация не обещает неизменяемый снимок при конкурентном добавлении данных.

| Список | Фильтры |
|---|---|
| equipment | q по inventory_number/serial_number/имени модели, category_id, model_id, operational_state, available, employee_id текущего получателя |
| employees | q по full_name/personnel_number, is_active |
| equipment-models | q по manufacturer/name, category_id |
| categories | q по name |
| assignments | equipment_id, employee_id, open; отсутствие open означает всю историю |

Поиск — регистронезависимая подстрока; спецсимволы поиска трактуются как текст,
а не пользовательский SQL. Фильтры действуют совместно через AND.

## Эксплуатационный минимум

- `/health/live`: процесс способен отвечать, не зависит от PostgreSQL.
- `/health/ready`: короткая проверка БД с тайм-аутом; 200 при готовности, 503 иначе.
- Структурированные логи: request_id, метод, шаблон маршрута, status, duration;
  без ФИО, email, тел запросов и секретов. Неверный request_id клиента не принимать без проверки.
- Ограниченный пул соединений, тайм-ауты соединений/запросов/блокировок;
  конкретные значения определить в реализации и проверить нагрузкой.
- Пагинация, ограничение длины полей и тела запроса. Никаких безлимитных списков.
- SIGTERM: прекратить приём новых запросов, дать текущим ограниченное время, закрыть пул.
- Метрики, трассировка, балансировка, резервное копирование и аварийное восстановление
  — последующие SRE-работы. Наличие PostgreSQL volume само по себе не резервное копирование.

## 12 Factor: реализованные решения

Основа — [The Twelve-Factor App](https://12factor.net/). Итоговая проверка каждого
фактора и её ограничения сохранены в compliance-audit.md.

| Фактор | Решение | Проверка |
|---|---|---|
| I. Codebase | Общий Git-репозиторий, frontend/backend как части проекта | Окружения собираются из известного commit |
| II. Dependencies | Явные manifests, lock-файлы, изолированная сборка | Сборка в чистом окружении |
| III. Config | Настройки backend из env; в Git только пример без секретов | Смена БД/портов без правки кода |
| IV. Backing services | PostgreSQL подключается по DATABASE_URL | Переключение на другой экземпляр конфигурацией |
| V. Build/release/run | Неизменяемая сборка; release добавляет конфигурацию и миграции | Тот же артефакт проходит через окружения |
| VI. Processes | Backend не хранит пользовательское состояние локально | Перезапуск и две реплики не теряют данные |
| VII. Port binding | Сервисы доступны через заданные сетевые порты | Запуск без привязки к конкретному хосту |
| VIII. Concurrency | Масштабирование числом backend-процессов | Две реплики используют общую БД |
| IX. Disposability | Быстрый старт, ограниченное завершение по SIGTERM | Проверка завершения активного запроса |
| X. Dev/prod parity | Одинаковая основная версия PostgreSQL и способ сборки | Нет SQLite вместо PostgreSQL в интеграционных тестах |
| XI. Logs | stdout/stderr, сбор вне приложения | Нет обязательных файлов журналов в контейнере |
| XII. Admin processes | Миграции и seed — отдельные команды той же версии | Не запускаются автоматически каждой репликой |

Frontend использует относительный `/api/v1`, поэтому для смены адреса backend не
нужно пересобирать JS. Если позже появятся публичные настройки, меняющиеся между
окружениями, отдавать их отдельной runtime-конфигурацией; не помещать туда секреты.
Reverse proxy получает адрес backend из конфигурации окружения при запуске.
Статические файлы frontend — артефакт сборки, а не изменяемое пользовательское состояние.

## Граница завершённого MVP

Проект завершён как учебная основа для SRE. Аутентификация, Kubernetes, метрики,
трассировка, резервное копирование и публичное развёртывание остаются отдельными
учебными расширениями и не входят в критерии MVP.
