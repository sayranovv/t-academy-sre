# SLI, SLO и SLA приложения учёта оборудования

## Приложение и выбор показателей

В этой работе я измеряю успешность выдачи, возврата и создания экземпляров оборудования. Ответственный за оборудование пользуется этими операциями в повседневной работе. Отдельный пробер проверяет доступность приложения, когда пользовательских запросов нет.

Приложение работает в minikube, профиль `sre`, namespace `default`. API имеет две реплики. VictoriaMetrics собирает метрики и хранит их семь дней. Графики доступны в vmui.

## Метрики

Из четырёх счётчиков прошлой работы я выбрал три. Одних успехов для расчёта SLI недостаточно, поэтому к каждому добавил счётчик технических ошибок.

| Операция            | Существующая метрика успехов  | Новая метрика ошибок                   |
| ------------------- | ----------------------------- | -------------------------------------- |
| Выдача              | `equipment_assignments_total` | `equipment_assignments_failures_total` |
| Возврат             | `equipment_returns_total`     | `equipment_returns_failures_total`     |
| Создание экземпляра | `equipment_created_total`     | `equipment_created_failures_total`     |

Все метрики имеют тип Counter. Счётчик успехов увеличивается после фиксации транзакции. При технической ошибке сервис увеличивает счётчик неуспехов и передаёт исключение дальше. Обработчик охватывает всю транзакцию, включая commit: сбой возможен и при её завершении.

Предметные отказы `DomainError` и конфликты `IntegrityError`, которые приложение обрабатывает как ожидаемые HTTP-ответы, исключаются из расчёта. Например, повторная выдача занятого экземпляра не означает техническую неисправность. Текущая реализация исключает все `IntegrityError`; для неизвестных нарушений ограничений это упрощение может скрыть дефект приложения.

Повторный возврат уже возвращённого оборудования не увеличивает ни один из двух счётчиков. Счётчик возвратов отражает фактические изменения состояния. Ошибки GET-запросов чтения списков не относятся к выбранным операциям и не увеличивают эти счётчики.

## SLI и формулы

Для операции i за окно W обозначаю число успехов как S_i(W), а число технических неуспехов как F_i(W).

```text
SLI_i(W) = 100 × S_i(W) / (S_i(W) + F_i(W))
```

Это Request Based SLI: единицей учёта служит результат операции в сервисе. При нулевом знаменателе показатель не определён. Пустой график не означает ни 0%, ни 100%.

Результат относится к завершению операции на backend. Счётчики не подтверждают получение HTTP-ответа клиентом и не учитывают запросы, которые до сервиса не дошли. Недоступность самого backend отдельно обнаруживает пробер.

У каждой реплики свои счётчики. В запросах сначала рассчитываю прирост каждой серии с учётом сбросов при перезапуске, затем суммирую приросты реплик.

### Выдача

```promql
100 *
sum(increase(equipment_assignments_total[10m]))
/
(
  sum(increase(equipment_assignments_total[10m]))
  + sum(increase(equipment_assignments_failures_total[10m]))
)
```

### Возврат

```promql
100 *
sum(increase(equipment_returns_total[10m]))
/
(
  sum(increase(equipment_returns_total[10m]))
  + sum(increase(equipment_returns_failures_total[10m]))
)
```

### Создание экземпляра

```promql
100 *
sum(increase(equipment_created_total[10m]))
/
(
  sum(increase(equipment_created_total[10m]))
  + sum(increase(equipment_created_failures_total[10m]))
)
```

## Пробер доступности

Пробер работает отдельным процессом в Deployment `equipment-prober`. Он использует тот же образ, что API, и запускает `python -m app.prober`. Для работы ему не нужны настройки подключения к БД.

Каждые 30 секунд он отправляет GET-запрос на `http://web:8080/health/ready`. Запрос проходит через Nginx к API. Обработчик готовности подключается к PostgreSQL и выполняет `SELECT 1`.

Проверка успешна, если приходит HTTP 200 и JSON с `status=ready`, `database=connected`, а время проверки не превышает 5 секунд. Ошибка соединения, тайм-аут, перенаправление, другой HTTP-статус или неверное тело ответа означают неуспех. Сетевой тайм-аут стандартного клиента не является строгим общим дедлайном с учётом DNS. Пробер также проверяет длительность после получения ответа.

После неуспеха пробер продолжает работу. Он публикует метрики на порту 9101, путь `/metrics`:

```text
probe_checks_total{result="success"}
probe_checks_total{result="failure"}
```

Обе серии инициализируются нулями. VictoriaMetrics обнаруживает Pod по аннотациям `prometheus.io/scrape`, `prometheus.io/port` и `prometheus.io/path`.

Обозначаю успешные проверки за окно W как P_ok(W), неуспешные как P_fail(W).

```text
SLI_probe(W) = 100 × P_ok(W) / (P_ok(W) + P_fail(W))
```

Запрос для демонстрации:

```promql
100 *
sum(increase(probe_checks_total{result="success"}[10m]))
/
sum(increase(probe_checks_total[10m]))
```

Это доля успешных синтетических проверок. Она даёт выборочную оценку доступности. Короткий сбой между проверками может остаться незамеченным. Правило классификации хороших и плохих минут я не вводил, поэтому результат не называю TBSLO.

Пробер проверяет внутренний путь через Nginx, API и БД. Он не проверяет браузер, внешний доступ к кластеру и результат реальной выдачи. Остановка локального `port-forward` не влияет на внутренние проверки. Если недоступен сам пробер или сборщик метрик, отсутствие наблюдений нельзя считать успехом. Состояние сбора проверяется отдельно по `up` соответствующего target.

## SLO

Для всех четырёх показателей я выбрал цель не ниже 99% за скользящие семь суток.

| Показатель                     | SLO   | Окно    |
| ------------------------------ | ----- | ------- |
| Успешность выдачи              | ≥ 99% | 7 суток |
| Успешность возврата            | ≥ 99% | 7 суток |
| Успешность создания экземпляра | ≥ 99% | 7 суток |
| Доступность по проберу         | ≥ 99% | 7 суток |

Порог 99% я выбрал как начальную цель учебного проекта. Статистики и требований реального заказчика для более точного выбора пока нет. После накопления данных цель можно пересмотреть.

```text
SLO_i выполнен, если SLI_i(7d) ≥ 99%
Бюджет технических ошибок = 1% учитываемых событий
```

Например, при 200 учитываемых операциях допустимы две технические ошибки: `198 / 200 × 100% = 99%`.

При проверке раз в 30 секунд за семь суток ожидается 20 160 проверок. Если все они выполнены, цель 99% допускает максимум 201 неуспешную проверку. Это бюджет проверок, а не точное число минут простоя.

Для недельного расчёта в приведённых запросах нужно заменить каждое `[10m]` на `[7d]`. Короткая история наблюдений не подтверждает недельный SLO.

## SLA

Для приложения я сформулировал соглашение с ответственным за оборудование: успешность каждой из трёх предметных операций должна быть не ниже 98% за скользящие семь суток. Область соглашения ограничена операциями, которые учитывают сервисные счётчики.

```text
SLA_i выполнен, если SLI_i(7d) ≥ 98%
Допустимая доля технических ошибок по SLA = 2%
```

Общий SLA выполнен только при одновременном выполнении трёх условий:

```text
SLI_issue(7d) ≥ 98%
AND SLI_return(7d) ≥ 98%
AND SLI_create(7d) ≥ 98%
```

Эквивалентно, при наличии данных по всем трём операциям:

```text
min(SLI_issue(7d), SLI_return(7d), SLI_create(7d)) ≥ 98%
```

Среднее между показателями не используется: успешное создание экземпляров не компенсирует проблемы выдачи. Если по операции нет учитываемых событий, её результат не определён, поэтому нельзя заявить о выполнении всего набора по остальным операциям.

При нарушении SLA ответственный за сервис уведомляет потребителя и готовит разбор причин с мерами по устранению. SLO выше договорной границы на один процентный пункт, чтобы реагировать на ухудшение до нарушения SLA.

Показатель пробера имеет отдельный SLO 99%. В общий предметный SLA он не включён.

## Изменения приложения

Для этой работы я добавил три счётчика технических ошибок в `backend/app/metrics.py`. В `backend/app/services.py` обработка ошибок охватывает транзакции выдачи, возврата и создания экземпляров. Для общей функции создания счётчик оборудования изменяется только при `resource == "equipment"`.

Модуль `backend/app/prober.py` выполняет проверки и экспортирует метрики независимо от API. Манифест `k8s/monitoring/prober.yml` описывает его Deployment и Service. API и пробер используют образ `t-academy-equipment-api:0.1.5`. Инструкция запуска находится в `docs/prober.md`.

В модульных тестах проверены технические ошибки во время операции и завершения транзакции, ожидаемые отказы и повторный возврат. Для пробера проверены ответы HTTP, неверный JSON, тайм-аут, продолжение работы после ошибки и экспорт метрик. Во время подготовки прошли 25 тестов этих модулей без подключения к рабочей БД. Сам эксперимент с остановкой PostgreSQL проверяет поведение развёрнутого приложения.

## Графики и эксперимент

В vmui я построил отдельные графики выдачи, возврата, создания экземпляров и доступности по проберу. На предметных графиках показал границы 99% и 98%, на графике пробера 99%.

Для демонстрации использую окно расчёта 10 минут и отображаемую историю 30 минут. Каждая точка SLI описывает предыдущие 10 минут. Границы на этих графиках служат для наглядного сравнения; выполнение недельных SLO и SLA оценивается отдельным расчётом за семь суток.

Эксперимент состоит из следующих действий:

1. При работающей БД выполнить создание экземпляра, выдачу и возврат. Проверить рост счётчиков успехов.
2. Сохранить данные для новых запросов: модель, активного сотрудника, свободный экземпляр, открытую выдачу и новый инвентарный номер.
3. Уменьшить число реплик `db-deployment` до нуля и дождаться удаления Pod. PVC `db-pvc` сохраняет данные.
4. Во время недоступности отправить POST создания оборудования, POST выдачи и PUT возврата. Показать технические ответы API и рост счётчиков ошибок.
5. Показать неуспешные проверки пробера и снижение SLI в vmui.
6. Вернуть одну реплику БД, дождаться ответа 200 от `/health/ready`, проверить записи и повторить операции.

Команды остановки и восстановления:

```bash
kubectl --context sre -n default scale deployment/db-deployment --replicas=0
kubectl --context sre -n default wait --for=delete pod -l app=db --timeout=120s

kubectl --context sre -n default scale deployment/db-deployment --replicas=1
kubectl --context sre -n default rollout status deployment/db-deployment --timeout=120s
```

Пробер обнаружил недоступность БД автоматически. После восстановления его SLI начал расти. Показатель не возвращается к 100% сразу: ошибки ещё находятся в окне. Возможны горизонтальные участки, когда новая успешная проверка заменяет старую успешную. Когда все ошибки выйдут из окна и новых не будет, SLI вернётся к 100%.

Эксперимент показывает реакцию индикаторов на сбой и восстановление. Полный период наблюдений за семь суток в этой демонстрации не накоплен, поэтому нельщя заявлять о подтверждённом выполнении недельных SLO или SLA
