# Учёт оборудования — учебный проект SRE

Внутреннее приложение: каталог оборудования, сотрудники, выдача и возврат.
Цель — понятный проект для домашних заданий Т-Академии: frontend + backend,
HTTP/REST, PostgreSQL, CRUD и принципы 12 Factor.

**Состояние на 2026-09-28:** реализован каркас этапа 2 — Vue/PrimeVue, FastAPI,
PostgreSQL и Alembic в Docker Compose. Предметные таблицы, CRUD и выдачи ещё впереди.
Текущая страница `/environment` техническая; она не заменяет выбранный дизайн каталога.

## Запуск

Нужны Docker Engine с Compose v2 и make. Python/Node на хосте для запуска не нужны.
Из корня репозитория:

```sh
cp .env.example .env
make dev
```

Открыть [приложение](http://localhost:5173) и [документацию API](http://localhost:5173/docs).
Копировать `.env.example` следует только при первом запуске, не поверх настроенного `.env`.
Для быстрого локального старта `.env` необязателен: Compose содержит учебные значения
по умолчанию. Они не предназначены для внешнего развёртывания.

`make dev` собирает образы и ждёт успешной последовательности: PostgreSQL готов →
одноразовые миграции завершены → API готов → frontend готов. Alembic пока имеет
пустую цепочку ревизий; первую предметную миграцию добавим на этапе 3.

| Команда | Результат |
|---|---|
| `make dev` | Собрать и запустить окружение в фоне |
| `make stop` | Остановить и удалить контейнеры, сохранить volume БД |
| `make migrate` | Отдельно применить миграции |
| `make test` | Backend-тесты с PostgreSQL и frontend-тесты в контейнерах |
| `make lint` | Ruff, проверка Python-форматирования, TypeScript и ESLint |
| `make build` | Собрать образы разработки и проверить production-сборку frontend |
| `make logs` | Следить за журналами контейнеров |
| `make seed` | Пока сообщает, что seed появится на этапе 3, и завершается с ошибкой |

Runtime-образы Nginx/backend и CI относятся к этапу 7; текущие образы предназначены
для разработки. Повторять `make dev` после изменения зависимостей. Исходники Vue и
Python подключены через bind mounts и обновляются без пересборки.

## Как проходит запрос

Браузер → `localhost:5173` (Vite) → `/api/v1/status` (FastAPI).
Проверка `/health/ready` проходит тем же путём и выполняет `SELECT 1` в PostgreSQL.
Браузер не знает адреса БД или её пароля. API и PostgreSQL не публикуют порты на хосте;
соединение идёт по внутренней сети Compose. Только frontend доступен на localhost.

`/health/live` проверяет, что процесс отвечает, без обращения к БД. `/health/ready`
проверяет БД с общим сроком ожидания 2 секунды, используя отдельное асинхронное
соединение только для этой пробы. Будущие бизнес-обработчики и SQLAlchemy-сессии
остаются синхронными. Проверка готовности пока не проверяет версию предметной схемы.

## Конфигурация и диагностика

Основные настройки в `.env.example`. Отдельные DB-поля превращаются в URL через
SQLAlchemy URL, без склейки пароля со строкой подключения. Backend также принимает
`DATABASE_URL` при прямом запуске процесса или передаче env контейнеру; он имеет
приоритет над DB-полями. Compose по умолчанию использует свой сервис `db`.

- Если Docker недоступен — запустить Docker Desktop и повторить `make dev`.
- Если 5173 занят — задать `WEB_PORT` в `.env` и повторить `make dev`.
- Статус контейнеров: `docker compose ps -a`; ошибки: `make logs`.
- После изменения логина/пароля уже созданной БД её пользователь автоматически
  не меняется: параметры POSTGRES_* используются при первом создании volume.
- Не использовать `docker compose down -v` для обычной остановки: это удаляет данные.
- Остановка/перезапуск сохраняет volume, но не является резервным копированием.
